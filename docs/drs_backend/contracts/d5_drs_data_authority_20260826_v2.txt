2. PRESERVED PRODUCT AND MODEL DECISIONS

LaiBE DRS storage only serves case decisions, versions, evidence, review, receipts and traceability. It is not a cloud drive, chat product, matching/lowest-bid platform, payment escrow or old-house investment product.

MODEL_OPTIONS:
- ONE_PRIVATE_BUCKET_PDF_ONLY=REJECTED because untrusted intake and formal evidence share one trust/lifecycle boundary and DRS photos/drawings are excluded.
- FOUR_BUCKET_STAGING_ORIGINALS_DERIVATIVES_EXPORTS=REJECTED_FOR_MVP because it multiplies policy, copy, backup and drift surfaces.
- TWO_PRIVATE_BUCKET_TRUST_BOUNDARY=ACCEPTED.

- drs-case-intake-private: untrusted staging/quarantine only; never formal evidence; expired unpromoted objects are cleanup eligible.
- drs-case-records-private: validated canonical sources, exact-version derived artifacts and formal snapshot outputs.

Both buckets are private. Buckets are named by DRS trust purpose, never by role or case. Roles/cases are rows and policies, not buckets.

- image/jpeg with .jpg or .jpeg
- image/png with .png

6. DATA AND REFERENTIAL MODEL

casework is the only case/document authority. No parallel public.drs case/document truth may be created.

- documents: PK(id), NOT NULL case_id, UNIQUE(case_id,id), logical kind/visibility/source role/status, nullable current_version_id projection.
- document_versions: PK(id), NOT NULL case_id/document_id, immutable version_no/actor/time/hash/size/detected MIME/validation/lifecycle, FK(case_id,document_id) to documents(case_id,id) ON DELETE RESTRICT, UNIQUE(case_id,document_id,id), UNIQUE(document_id,version_no).
- documents current version: composite FK(case_id,id,current_version_id) to document_versions(case_id,document_id,id), so it cannot point across case/document. Only the sole finalize/supersede function updates it.
- document_version_sources: exactly one canonical source for every FORMAL version; PK(case_id,document_id,version_id), composite FK to document_versions, NOT NULL bucket/key/hash/size/MIME/validation, UNIQUE(bucket_id,object_key). A deferred constraint trigger requires source count exactly one when version state is FORMAL.
- document_artifacts: derived/output only; composite FK(case_id,document_id,version_id) to versions, SOURCE kind forbidden, UNIQUE(bucket_id,object_key).
- document_upload_intents: one file each; server-owned case/document/path/expected facts/nonce/idempotency/expiry/state. A staging receipt is not a version.
- evidence_references: exact case_id/document_id/version_id composite FK to versions plus page/region/item locator. Any review/event subject uses same-case FK/check.
- submission_snapshots: UNIQUE(case_id,id), immutable canonical payload hash. snapshot_items have both FK(case_id,snapshot_id) to snapshot and FK(case_id,document_id,version_id) to version.
- receipts/events/intents carry case_id and composite FKs to referenced version/snapshot. Generic subject_id without referential validation is not authority.
- LINE, Calendar and formal review consumers only keep typed opaque exact-version refs resolved by server API. They receive no bucket/path/service-role/URL-minting permission.
- public.drs_case_audit_events may reference the canonical case event/receipt ID for DRS workflow audit; it cannot become a second formal document/event truth.

All metadata/evidence/snapshot/receipt tables ENABLE and FORCE RLS. Foreign keys and current-authority lookup fields are indexed. Cross-case/cross-document linkage must be impossible by constraints or the sole atomic function.

7. LIFECYCLE AND ATOMICITY

Formal source/version/evidence/snapshot/receipt/event are append-only. Records objects prohibit upsert and in-place replace.
- Replace creates a new version.
- Supersede preserves the old version; existing evidence stays pinned and becomes revalidation-required where applicable.
- Withdraw appends a state/event, stops new access grants and new references, and preserves history.
- Only expired unpromoted intake objects may be cleanup-deleted with a cleanup receipt.
- Formal hard delete/legal purge is outside MVP and needs separate Human authority.

Promotion saga:
intake upload -> structural validation and malware scan -> copy to unique records path with no upsert -> verify served object hash/size -> sole short DB finalize transaction -> cleanup intake.
Storage work occurs before the transaction. The transaction locks in fixed order document then intent/version; verifies idempotency and same-case/source-count invariants; inserts version/source/event/receipt and updates current projection. DB failure creates an orphan-cleanup work item and no formal receipt/version. Same document plus same verified SHA retry returns the same version/receipt. Same idempotency key with different payload conflicts. Concurrent finalize has one winner.

10. SIGNED CAPABILITY TRUTH

Supabase native signed upload URL requires no further auth and is valid for 2 hours. It is only issued for a unique intake path with upsert=false. Application intent TTL is 15 minutes; a later native upload remains quarantine-only and is cleaned after 24 hours. The token is not cryptographically one-time; unique key/no-upsert gives at most one successful creation, while finalize idempotency controls the state transition.

Private signed download remains replayable until expiry and is not instantly revocable. Default download is current-authority BFF streaming. Any future direct link is at most 60 seconds and never used for raw intake or sensitive history. A true one-time download requires a separate server one-time ticket/proxy.
